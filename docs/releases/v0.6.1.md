If you terminate TLS, 0.6.0 does not work and this release is the fix. If you
do not, nothing here changes anything for you.

## TLS was dead on arrival in 0.6.0

**Any listener with a `tls` block crashed the process at startup**, on every
platform 0.6.0 shipped — before accepting a connection, while reading the
private key. Plaintext-only configurations on the same binary were fine, which
is why this survived to a release: the failure needs a `tls` block to appear at
all.

There is no configuration change and no workaround. 0.5.1 was unaffected;
anything terminating TLS should move straight to 0.6.1.

The cause was the build, not the proxy. 0.6.0 was the first release to compile
OpenSSL from source through the Zig toolchain (that was the point of it), and
Zig instruments C with undefined-behaviour checks in the build mode releases
use. One of those checks fires on an idiom OpenSSL has always used — calling a
free function through a cast pointer — so libcrypto trapped on correct code the
first time it parsed a key. The vendored libcrypto is now built the way every
other libcrypto is: without that instrumentation.

`src/` is untouched. Same proxy, same protocol handling, same libcrypto version
(OpenSSL 3.5.7) — it is now compiled so that it runs.

## The gate that should have caught it

zoxy's live gate has terminated real TLS on every change for months, and it
passed throughout, because it — like every other gate — ran a debug build, and
debug builds do not carry the instrumentation that broke the release. The gate
was testing a different program from the one being published.

`zig build ci` now runs that same live gate twice: once against the default
build, and once against a binary built the way releases are. Same requests,
same TLS listener, same assertions; the only difference is the build
configuration, which is the thing that was never covered.

## Upgrading

Replace the binary. No configuration, CLI or behavioural changes.
