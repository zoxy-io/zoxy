**zoxy now speaks HTTP/2 to its clients.** It is off until a listener
asks for it, and a config that does not ask reserves no session or stream
for it. One thing
changes even if you change nothing: a listener that terminates TLS now
answers ALPN, and a client that offers only `h2` to a listener without
it is refused in the handshake instead of being handed HTTP/1.1. See
[Upgrading](#upgrading).

## HTTP/2, to the client

An `http` listener reaches HTTP/2 two ways:

- over TLS, by offering `h2` in the new `tls.alpn`;
- in the clear, by `"h2c": true`, which answers a client that opens with
  HTTP/2's preface (prior knowledge, RFC 9113 §3.3) and serves HTTP/1.1
  as before to one that does not.

```json
"listeners": [
    { "bind": "0.0.0.0:443", "http": { "cluster": "web" },
      "tls": { "cert": "/etc/zoxy/site.crt", "key": "/etc/zoxy/site.key",
               "alpn": ["h2", "http/1.1"] } }
],
"limits": { "stream_slots": 4096 }
```

Each stream is one request. It goes through the same routing, filters,
redirects, access log and metrics as an HTTP/1.1 request, to the same
pooled HTTP/1.1 upstream. The origin leg stays HTTP/1.1, and a request
body with no length goes to it chunked.

The request crosses over by being written out as the HTTP/1.1 head it
stands for, then parsed back by the same parser every HTTP/1.1 request
meets. That is deliberate. Every rule zoxy holds a request to, the
request-smuggling defences first, is stated once, against the bytes the
origin will read. A second set of rules over HTTP/2's fields would be a
second trust boundary to keep in step with the first, and that gap is
where smuggling lives. The answer comes back the same way: the rendered
HTTP/1.1 response, with every response filter already applied, is read
back and said again as HTTP/2.

Two new limits size it:

- `limits.stream_slots` is required wherever a listener speaks HTTP/2,
  and has no default. It bounds the requests in flight across every
  HTTP/2 connection at once. A stream past it is refused
  `REFUSED_STREAM`, which a client retries, and counted in
  `zoxy_h2_shed_streams`. One connection advertises at most 100.
- `limits.h2_connections` bounds the connections speaking HTTP/2 at
  once, and defaults to 1024. With none free, a listener offering `h2`
  beside `http/1.1` offers `http/1.1` alone in the handshake, an h2c
  preface is closed (`zoxy_h2_shed_sessions`), and a listener offering
  `h2` alone sheds the connection at accept, before its handshake
  (`zoxy_shed_h2_sessions`).

What fails on a stream ends that stream, reset or answered `502`/`504`,
never the connection. §8's shedding ladder now says, rung by rung,
whether an HTTP/2 client loses the stream or the connection.

A connection is told before it is closed: `GOAWAY(NO_ERROR)` on a drain,
on the idle timeout with no stream open, and when it reaches
`keepalive_requests`. For that cap, a stream is a request: the stream
that reaches it is served, the GOAWAY names it, and later ones are
refused for the client to retry on a new connection. It is counted in
`zoxy_l7_keepalive_requests_capped`, once per connection.

## What a client cannot make it spend

What an HTTP/2 client spends is budgeted per connection, and an overrun
ends the connection with `GOAWAY(ENHANCE_YOUR_CALM)`, each budget counted
in its own `zoxy_h2_calm_*`:

- **Rapid Reset** (CVE-2023-44487): resetting streams before their
  answers end, faster than answers end.
- **Floods of frames that ask for nothing**: PING, SETTINGS,
  WINDOW_UPDATE, PRIORITY and unknown frame types, empty DATA.
- **CONTINUATION floods**: a field block spread over more frames than the
  assembler allows.
- **HPACK bombs**: a field block, or the header list it decodes to, past
  what the connection advertised.

## What it does not do

- **HTTP/2 to the origin.** Every upstream leg is HTTP/1.1.
- **Trailers**, in either direction, so **gRPC does not work through
  it**: gRPC's status travels in trailers.
- **Extended CONNECT** (RFC 8441) is never offered, so WebSocket over
  HTTP/2 is refused at the stream. Browsers that find it unoffered open
  their WebSockets on a separate HTTP/1.1 connection, so keep `http/1.1`
  in `alpn` on a listener that tunnels upgrades.
- **`Upgrade: h2c`** stays refused, `501`, as before. h2c is prior
  knowledge only.

## A terminating listener now answers ALPN (#271)

Through 0.9.1 a listener that terminated TLS ignored ALPN. Every client
got HTTP/1.1, whatever it offered, and a client offering only `h2` would
then speak HTTP/2 into a parser that cannot read it. Now:

- With no `tls.alpn`, an `http` listener offers `http/1.1`. A client
  offering `h2, http/1.1`, as browsers and curl do, gets `http/1.1`
  selected, which is what it was speaking already.
- A client that offers no ALPN at all is unaffected.
- A client whose offer names nothing the listener speaks, such as a
  gRPC client offering only `h2`, is refused in the handshake with the
  `no_application_protocol` alert RFC 7301 requires, and counted in
  `zoxy_tls_alpn_refused`. It is not counted as a handshake failure.
- An `l4` listener relays bytes it never parses, so it offers nothing,
  and `tls.alpn` is refused there.

## Checked against

- **h2spec**, an RFC 9113 suite sharing no code with zoxy, runs against
  the shipped ReleaseSafe build over h2c and TLS, a merge-tier gate like
  the bench (`zig build h2spec`).
  Its first run failed 7 of its 145 cases. Five were zoxy's to fix and are
  fixed: a frame after the client's own reset, or on a stream both halves
  closed, is `STREAM_CLOSED`; no stream may depend on itself; a stream's
  window takes one full frame. The other two are decisions DESIGN.md §12
  records, and the gate fails if h2spec's failures ever differ from them:
  - an h2c listener answers an invalid preface as the malformed HTTP/1.1
    request it is, with `400`, rather than closing;
  - a header list past the advertised `SETTINGS_MAX_HEADER_LIST_SIZE`
    ends the connection with `ENHANCE_YOUR_CALM` rather than a `431` on
    the stream, because the decoder stopping there is the HPACK-bomb
    defence.
- **The simulator speaks HTTP/2.** A share of every seed's population is
  h2c clients, a third of them flooding one budget each, beside the
  HTTP/1.1 and L4 clients under one schedule. Its first sweep found three
  bugs. The nightly soak's first runs with the flood clients found two
  more. In each, something reached a session that had already ended its
  connection, while the GOAWAY saying so was still going out: a drain,
  or an origin's answer arriving after a flood's verdict. Both tripped
  an assertion. All five are fixed.
- **The live gate** runs an h2c leg against the shipped binary, and
  `zig build bench` gains an HTTP/2 band, driven by zrk.

## What it costs

`zoxy --check` on the same configs, 0.9.1 against 0.10.0:

| config | 0.9.1 | 0.10.0 | what moved |
|---|---|---|---|
| `config/example.json` | 47,371 KiB | 47,503 KiB | conn slot 512 → 536 B, stream slot 1,552 → 1,624 B, labeled metrics +2,116 B |
| one terminating listener | 239,178 KiB | 239,326 KiB | the same, plus a TLS engine 94,448 → 94,464 B |

The banner gains a line, `h2 sessions 0 x 0 B + stream heads 0 x 0 B`,
for a config that speaks no HTTP/2. fds and the ring do not move.

Turning HTTP/2 on is where the memory goes. The terminating listener
above, with `"alpn": ["h2", "http/1.1"]` and `stream_slots` at 4096,
prices at 373,215 KiB, about 131 MiB more:

- 1,024 sessions × 94,512 B: 92 MiB, the default `h2_connections`;
- 4,096 stream heads × 8,216 B: 32 MiB;
- 4,096 more stream slots × 1,624 B: 6 MiB.

A session is the largest new unit, so size `h2_connections` to the
HTTP/2 connections you expect at once, not to `conn_slots`.

## Under the hood

- **One connection, many exchanges.** An exchange used to be keyed on
  its connection. It is now keyed on a stream (`net/Stream.zig`), drawn
  from two pools: one admission stream per connection, as before, and the
  shared streams `stream_slots` sizes. HTTP/1.1 runs on the first exactly
  as it did.
- **zoxy-io/h2** is a new dependency, pinned by hash and audited as one:
  RFC 9113's frames and §8 rules, with HPACK beneath. It holds no
  allocator, and the lint confines it to `src/http/h2/`. The session
  built on it is zoxy's own and sans-I/O.
- **zssl** moves to 5f5c582 for server-side ALPN as a preference list,
  with its re-audit record in `build.zig.zon`.
- CI installs Zig with setup-zig, pinned to `minimum_zig_version`
  (0.17.1), instead of a devenv shell.

## Upgrading

Replace the binary. Every 0.9.1 config loads unchanged: the schema only
gains keys (`http.h2c`, `tls.alpn`, `limits.stream_slots`,
`limits.h2_connections`), and its memory budget grows by 132 KiB on the
example config, 0.3%.

The one change you may see is ALPN on a terminating listener. A client
that offered only `h2` used to be handed HTTP/1.1. If it really spoke
HTTP/1.1 anyway, it worked by accident; it is now refused in the
handshake. Watch `zoxy_tls_alpn_refused` after the upgrade. If it is not
zero, those clients want HTTP/2, and serving them is
`"alpn": ["h2", "http/1.1"]` plus `limits.stream_slots`.

New counters: `zoxy_tls_alpn_refused`, `zoxy_shed_h2_sessions`,
`zoxy_h2_connections`, `zoxy_h2_shed_sessions`, `zoxy_h2_shed_streams`,
and eight `zoxy_h2_calm_*`, one per budget.
