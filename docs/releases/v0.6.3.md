Two correctness fixes at ingress, one of them security-relevant, and both
faster than the code they replace. **This release changes what zoxy accepts.**
Read the upgrading section before rolling it out.

Both bugs are the same shape: the head parser's character tables said what was
*invalid* and accepted everything else. Denylists fail open. Both are present
in 0.6.2 and every release before it.

## A backslash in the request-target could desync routing from the origin

This is the one to upgrade for. The request-target table rejected only
controls, space and DEL, so a target could carry `"<>\^`{|}` and every byte
from 0x80 up — none of which RFC 3986 allows unencoded.

`\` is the character that matters. IIS, .NET and browser URL parsing normalize
a backslash to `/`. So zoxy routing on

    GET /public\..\admin HTTP/1.1

matched a `/public` route, forwarded the target verbatim, and an origin that
resolves `\` as a separator read `/admin`. Proxy and origin took two different
paths out of one request-target — the same failure as disagreeing about a line
terminator, and it reaches path-based routing and any authorization built on
it. zoxy's own `validateTarget` checks the target's *form* — origin-form,
absolute-form, `*` — and never its character class, so nothing on this side
caught it.

The table is now RFC 3986 `pchar`, built from the grammar rather than
subtracted from it. `#`, `[` and `]` are tolerated against the letter of the
spec: a fragment fails safe (an origin truncating there sees *less* path than
the proxy did, never more) and brackets are ubiquitous in query strings.

**This is byte-level agreement, not safe path routing.** The dominant path
confusions are percent-encoding and dot-segments; those are normalized by
`canonicalTarget` and always have been. What changed is that the proxy and the
origin can no longer read different *bytes* as different paths.

## A header field name was not held to its grammar

The same shape, one layer down. The field-name table listed controls, space,
colon and DEL as invalid and accepted the other 144 bytes that are not
`tchar`: the RFC 9110 §5.6.2 delimiters `"(),/;<=>?@[\]{}` and all of
0x80-0xff. A field name is `token`, the same grammar as a method — and the
method table had been the correct allowlist all along.

Forwarding a field name the backend may tokenize differently is how two ends
come to disagree about which headers a request carried. It is now that table.

## Also faster

Unusually for fixes in this class, both are wins.

The field-name scan lost its vector path. That path's `> ' '` range compare is
exactly what admitted the 144 bytes, and `tchar` is not a range; an exact
classifier was written and measured at 1.24x *slower* before being discarded.
Field names are too short for a 16-byte setup to amortize. The byte-at-a-time
loop replacing it is 0.85x.

The target scan **kept** its vector path — the opposite call, for the opposite
reason: a target with a query string routinely runs to hundreds of bytes.
Measured both ways, scalar-only came out 1.03x on an 8-byte target but 1.30x
on a 165-byte one. Stating the allowed set as a reject mask then landed at
0.99x, because one wrapping subtract and one compare catch controls, space,
DEL and all of 0x80-0xff together.

A third change is internal: the header-value scan loses a middle SWAR tier
that only ever saw the tail of the buffer and could not express "a tab is
legal" in its arithmetic. Worth about 1% in this build's configuration, and
30 lines of bit arithmetic gone with it.

## Upgrading

Replace the binary. No configuration or CLI changes.

**Check your ingress first — this release rejects requests 0.6.2 forwarded.**
Both changes answer 400. In rough order of how likely you are to hit them:

- **Raw non-ASCII in a request-target.** `GET /café` now fails; `GET /caf%C3%A9`
  is fine. RFC 3986 has always required the encoded form and browsers send it,
  but hand-written clients, crawlers and internal tooling often do not. This is
  the change most likely to affect a working deployment, and it is a deliberate
  trade rather than an oversight.
- **A raw `"`, `<`, `>`, `^`, `` ` ``, `{`, `|`, `}` or `\` in a target.**
  Percent-encoded, all nine are still accepted and forwarded unchanged.
- **A header field name outside `tchar`** — the letters, the digits, and

      ! # $ % & ' * + - . ^ _ ` | ~

  The hyphen and underscore of an ordinary custom header are fine.

If you cannot rule out non-ASCII targets, stage this one.
