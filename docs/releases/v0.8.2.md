Performance. The L7 exchange path read a wall clock twice on every
request and took four locked counter updates; both are gone. No
configuration changes, no metric names or values change, and the one
behavioural difference is an improvement: durations are now measured on a
monotonic clock, so an NTP step can no longer land inside one.

## The exchange path read a wall clock twice per request

0.8.0 completed the RED triad (#299) — errors and duration beside rate,
so a scrape could answer "how slow" and not only "how many". Measuring a
duration needs a stamp at each end of an exchange, and the version that
shipped took both from `CLOCK_REALTIME`, the clock the access log already
used for its timestamps.

The access log is off by default, and it had always been the *only* reader
of that clock, so its stamp was guarded: with no log configured, the
request path read no clock at all. #299 needed a duration in every
deployment — gating the histogram on a log sink would have left the
default install reporting no latency — so it removed the guard and added a
second unguarded read at the end of the exchange.

The result was a path that read no clock becoming one that read
`CLOCK_REALTIME` twice per request, log or no log.

An A/B profile of 0.7.0 against 0.8.1 (pinned core, real origin, fixed
100 k req/s, ReleaseSafe both sides) measured **~380 more userspace cycles
per request**, with io_uring submissions and completions per request
identical at 4.01 — compute, not I/O. L4 was unaffected, because an L4
relay runs no HTTP exchange.

The duration never needed a wall clock. It needed a stopwatch, and the
event loop's own per-tick clock had been one all along — it was only too
coarse to resolve tens of microseconds. It is precise now, refreshed once
per tick through the same read the loop already makes to arm a timer, so
both stamps come from a clock that has already been read by the time an
exchange asks for it. Re-profiled, `clock_gettime` no longer appears on
the request path at all.

## Durations are measured on a monotonic clock

This is the one operator-visible change in behaviour, and it is a
correction. `zoxy_cluster_duration_seconds` and the access log's
`duration_us` are now measured on `CLOCK_MONOTONIC`.

Before, both were derived from the wall clock, which NTP steers and can
step backwards. A step landing inside an exchange produced a wrong
duration for it — clamped rather than wrapped, but wrong. A monotonic
clock cannot step, so the interval is now the interval.

The access log's `time` field is unchanged and still comes from the wall
clock: a line has to say *when* on a calendar an operator shares, and no
monotonic clock can answer that. It is read once per logged request now
rather than twice, and only when a log sink is configured.

## Counters are no longer atomic

Every counter was a relaxed atomic, which on x86 makes each increment a
`lock`-prefixed read-modify-write — and #299's histogram took four of them
per exchange. zoxy runs one thread that owns one io_uring and every pool;
scale-out is separate processes behind `SO_REUSEPORT`, never threads
sharing memory. The metrics endpoint is served on that same loop, and the
last asynchronous reader went away in 0.8.0 when SIGUSR1 stopped dumping
counters. Nothing was reading them from another thread, so the ordering
was buying nothing.

Counter names, values and semantics are identical. This is purely what it
costs to write one.

## What this release does not claim

The two figures above — the clock reads and the locked increments — are
exact, because they are the disappearance of specific symbols from the
profile rather than a shift in an aggregate.

A precise "and therefore N% faster overall" is not offered, and should be
treated with suspicion if you see one for a change this size: repeated
runs of the same binary on the same box span a range comparable to the
difference being measured. What remains between 0.7.0 and this release is
the priced cost of what 0.8.0 actually added — the per-stream state split,
richer route matching, and the latency histogram's own bucket walk — not
leftover clock cost.

## Under the hood

The per-tick clock going precise supersedes the coarse-clock change #39
made, which had stood since before 0.1.0. That measurement is not
overturned: it priced a
precise read taken on every *deadline refresh*, where this is one per
*tick*, against the two per *request* it removes. `IMPLEMENTATION_NOTES.md`
records both, and the note that a clock read's cost is a property of the
deployment — where the host clocksource falls back from TSC, or a VM has
no stable one, `clock_gettime` is a syscall rather than a vDSO call and the
removed reads would have cost roughly thirty times more.

## Upgrading

Replace the binary. No configuration change is required, nothing in
0.8.1's vocabulary moved, and a 0.8.2 binary loads every 0.8.x config
unchanged. Downgrading is equally free.

If you graph `zoxy_cluster_duration_seconds`, expect no visible change
except during an NTP step, where the old series could show a duration that
never happened.
