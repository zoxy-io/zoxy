The relay buffer is the operator's to size now, and its default moves from
4 KiB to 16 KiB. **This changes zoxy's memory footprint**: the advertised
pool total at defaults goes from ~34 MiB to ~66 MiB. Read the upgrading
section before rolling it out.

## One constant was deciding two things

`relay_buffer_bytes` set how many round trips a body costs — §6's strict
recv→send→recv relay is correct at any size, so a 256 KiB response was 64
round trips at 4 KiB. It also set the size of every TLS record a
terminating listener emits, because `tls_app_chunk_bytes` was an alias of
it. RFC 8446 caps a record's plaintext at 2^14 = 16 KiB, and haproxy's
`tune.bufsize` defaults to exactly that — so zoxy was emitting
quarter-size records against a peer emitting full ones, while already
*decrypting* full ones. That asymmetry is what gave it away.

Measured on the large-body band (256 KiB per response at ~100 MiB/s),
four runs alternating in one session, p50:

    zoxy L7 TLS   4 KiB [1248, 1199]  ->  16 KiB [745, 858]   -35%
    zoxy L7       4 KiB [1069, 1050]  ->  16 KiB [601, 600]   -43%
    zoxy L4       4 KiB [1081, 1105]  ->  16 KiB [722, 573]   -35..-48%

haproxy https held [722, 788] across all four runs as a control, which is
what rules out session drift. On that band zoxy goes from 58% behind
haproxy to roughly parity.

Nothing else moved. The keep-alive and close bands are unchanged — this
is a bulk-transfer fix, and a deployment serving small responses will see
no latency difference at all.

## What it costs

The relay pool is `relay_buffers × 2 × relay_buffer_bytes`, so the default
change quadruples that term: ~11 MiB to ~43 MiB at the default 1386
buffers, and ~90 MiB to ~358 MiB at the c10k ceiling. The TLS engine
outbox grows with it. Measured end to end, the bench configuration's RSS
went from 246 MiB to 295 MiB.

## Upgrading

Replace the binary. Existing configs keep working — the new limit is
optional and defaults to 16 KiB.

**Check your memory headroom first.** zoxy prints its full budget at
startup and asserts it, so a box that cannot afford the new default will
say so immediately rather than degrade. If you are memory-constrained, or
running many connections with small bodies, set it back:

    "limits": { "relay_buffer_bytes": 4096 }

That restores 0.6.3's footprint exactly. The knob accepts 1 KiB to 16 KiB;
values outside that range are refused at startup with
`LimitRelayBufferBytesOutOfRange`.

**Who should leave the default alone:** anyone proxying bodies larger than
a few KiB, and anyone terminating TLS. **Who should turn it down:** high
concurrency with small responses — an API gateway serving JSON, where
4 KiB was always the right size and the extra memory buys nothing.
