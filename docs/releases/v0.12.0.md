**A cluster now rides out a partial outage, and one TLS listener can
serve many names.** Every new feature is off until a config asks for it.
But this is the last release before the config freezes for 1.0.0, so it
also settles the config's shape, and some 0.11.0 configs will not load.
[Upgrading](#upgrading) lists each change and its replacement. One
long-standing bug is fixed with it: from v0.8.0 to v0.11.0 there was no
working way to set `keepalive_requests` (see [Fixes](#fixes)).

## Riding out a partial outage

0.11.0 had one answer to unhealthy origins: steer around them, and fail
open once none was left. Each addition below is a key on the cluster,
and a cluster without it behaves exactly as before.

- **Panic threshold.** `"panic_threshold_percent": 50` stops steering by
  health once less than half the cluster's routable weight is healthy.
  Otherwise the few healthy endpoints left would take the whole load,
  which is what ejects the next one. It accepts 1 to 99, and needs a
  `check` or `passive_ejection` to have anything to eject.
- **Standby endpoints.** An endpoint object may carry `"priority": 1`
  (up to 7; 0, the default, is the primary). A pick uses the lowest
  tier that has a healthy endpoint with room. Primaries at their
  `max_inflight` spill their excess to the next tier. A tiered cluster
  fails over to a healthy standby before its panic threshold reopens
  an ejected primary. Tiers are relative: the lowest one a cluster
  names is its primary.
- **Slow start.** With `"slow_start_ms": 30000`, an endpoint back from
  ejection gets an in-flight cap that rises linearly from 1 to its
  `max_inflight` over the window. The first origin to recover no
  longer takes every new request at once. It needs `max_inflight`.
- **Passive backoff.** `passive_ejection.recovery_ms_max` doubles a
  flapping endpoint's cooldown at each passive ejection, up to the
  ceiling. An endpoint that stays in rotation for a whole ceiling
  starts over at `recovery_ms`.
- **A cap on the whole cluster.** `"max_total_inflight": 64` bounds a
  cluster's in-flight work across all its endpoints, so slow origins
  behind one route cannot hold the shared upstream pool. A new HTTP
  request past it is answered `503`; a new L4 connection is closed. A
  retry of a request already admitted is never refused by it.
- **A retry budget.** `"retries": { "count": 2, "budget": 8 }` bounds the
  retry dials a cluster has in flight at once. When a whole set of
  origins starts refusing, the retries no longer pile onto them. A
  refused dial that finds the budget spent gets the `502` it would have
  had without retries. The bare number, `"retries": 2`, is still the
  short spelling.
- **Probe jitter.** No key. Each process starts its first health sweep at
  a random point in the first interval, so a fleet started together no
  longer probes its origins in lockstep.

Every pick that lands on an ejected endpoint, in panic, or on a standby
is now counted, as a process total and per cluster.

## Mutual TLS

A terminating listener can require a client certificate:

```json
"tls": {
    "cert": "/etc/zoxy/cert.pem",
    "key": "/etc/zoxy/key.pem",
    "client_ca": { "path": "/etc/zoxy/clients-ca.pem" }
}
```

The bundle is read at startup. A client's chain must reach one of its
CAs, be valid now, and start with an end-entity certificate.

- **`verify`.** It is `"required"` by default: a client that presents
  nothing is refused with the `certificate_required` alert.
  `"optional"` lets such clients in unauthenticated while a fleet
  migrates, but a certificate that is presented must still verify.
- **The identity.** It is the leaf's SHA-256 fingerprint. The origin
  receives it on every request as `X-Client-Cert-SHA256`, and the
  access log as `client_cert_sha256`.
- **The header is zoxy's alone.** An inbound `X-Client-Cert-SHA256` is
  stripped on every HTTP listener, mutual TLS or not, and no filter may
  set or remove it.
- **Not checked.** Neither revocation nor extended key usage is
  checked. Issue short-lived client certificates from a CA that issues
  nothing else.

## Many names on one listener, and RSA certificates

`certificates` lists further certificate and key pairs beside the
listener's own. Each connection gets the one whose names cover the
server name in its ClientHello (SNI):

```json
"tls": {
    "cert": "/etc/zoxy/default.pem",
    "key": "/etc/zoxy/default.key",
    "certificates": [
        { "cert": "/etc/zoxy/api.pem", "key": "/etc/zoxy/api.key" },
        { "cert": "/etc/zoxy/wildcard.pem", "key": "/etc/zoxy/wildcard.key" }
    ]
}
```

- **Where the names come from.** Each certificate's subjectAltName DNS
  entries, read at startup. The common name is not consulted, and there
  is nothing to list in the config.
- **Matching.** An exact name first, then a one-label wildcard
  (`*.example.com` covers `api.example.com`, not `example.com`), then
  the default pair in `cert` and `key`. A client that names nothing
  gets the default too.
- **Limits.** A process loads at most 256 certificates across all its
  listeners. A listed certificate that names no DNS host stops startup,
  since no client could ever be shown it.

**RSA keys** of 2048 to 4096 bits are now accepted, signing RSA-PSS. They
were refused because handshakes sign on the event loop, and an RSA
signature is far slower than an ECDSA one. On the bench host, one
signature costs:

| Key | One signature |
|---|---|
| ECDSA P-256 | ~15 µs |
| RSA 2048 | ~0.5 ms |
| RSA 4096 | ~2.4 ms |

Configuring an RSA key is the opt-in, and `zoxy_tls_rsa_signed` counts
every handshake one signed. A listener may hold an ECDSA and an RSA
certificate for the same name. Each client then gets the ECDSA one if
its `signature_algorithms` can verify it, which every TLS 1.3 client's
must, and the RSA one only otherwise.

## Fixes

**`keepalive_requests` is honoured again.** v0.8.0 moved it from `limits`
to the `http` listener, but only half the move landed. From v0.8.0
through v0.11.0, the documented `http.keepalive_requests` was refused as
an unknown field. `limits.keepalive_requests` still loaded, and nothing
read it. Every HTTP/1.1 connection was capped at 1000 requests,
whatever the config said. The key now works on the `http` listener, and
the `limits` copy is refused.

**An `http` probe of a `unix:` endpoint sends `Host: localhost`.** It
sent `Host: unix:/run/app.sock`, which a strict origin answers `400`, so
the endpoint never came up. A `host` on the check still overrides it.

**Keys that loaded and did nothing are refused** rather than accepted
silently:
- `retries` on an HTTP/2 (`h2c` or `h2`) cluster, whose connections are
  dialed by the origin pool, not by a request;
- `expect_status` on a `tcp` or `grpc` check;
- `"service": ""` on a `grpc` check (leave it out to ask about the whole
  server).

## Checked against

- **The gates.** Every change passed the unit and fuzz corpus, the lint,
  4,096 simulator seeds with the census, and the live gate in both the
  default and the shipped ReleaseSafe build.
- **The live gate** now also drives two TLS handshakes from
  `std.crypto.tls`, an implementation that is not zoxy's:
  - one naming a second certificate's host, which completes only if
    zoxy chose that certificate by SNI;
  - one naming an RSA certificate's host, which must complete RSA-PSS
    and move `tls_rsa_signed` by exactly one.
- **h2spec.** It matched DESIGN §12's recorded deviations: 145 cases over
  h2c with 1 recorded failure, and 145 over TLS with none.
- **Fuzzing.** It covers the new certificate-name and ClientHello parsing.
  The ClientHello target's seeds were found to be losing their first
  four bytes, so no run had ever started from a whole hello. With that
  fixed, a million runs were clean once the target's own oracle was
  corrected; the oracle had been wrong, not the parser.
- **The soak.** A run on this release's code passed: 4 × 1,000,000
  seeds, 488,000,001 to 492,000,000,
  [run 44356260484](https://github.com/zoxy-io/zoxy/actions/runs/44356260484).
- **Known gaps.**
  - The simulator holds one certificate per listener, so certificate
    selection is covered by directed tests and the live gate, not by
    seeded sweeps.
  - It cannot sign RSA, which has no deterministic signatures, and asks
    for no client certificates. Both counters are census-exempt with the
    reason recorded.
  - #391's ramped cap is not exported as a gauge; the in-flight gauge and
    the shed counters show the ramp working.

## Upgrading

Some 0.11.0 configs fail to load. Each fails at startup or under
`--check` with an error naming the problem; nothing changes meaning
silently.

| 0.11.0 | 0.12.0 |
|---|---|
| `limits.keepalive_requests` | `http.keepalive_requests` on each HTTP listener. The old key was ignored; see [Fixes](#fixes) |
| `limits.stream_slots` | `limits.h2_streams` |
| `limits.h2_origin_connections` | `limits.upstream_h2_connections` |
| `limits.h2_origin_streams` | `limits.upstream_h2_streams` |
| `*` anywhere in a route `host`, filter `match.host`, redirect host or l4 `sni` | Refused (`RouteHostWildcard`). It never matched anything; the spelling is held for a future wildcard rule |
| `retries` other than 0 on an `h2c` or `h2` cluster | Refused (`ClusterRetriesOnHttp2`); it was ignored |
| `expect_status` on a `tcp` or `grpc` check | Refused; it was ignored |
| `"service": ""` on a `grpc` check | Refused; omit `service` instead |

Load-error names that spelled the renamed keys follow them:
`LimitStreamSlots*` became `LimitH2Streams*`, `LimitH2Origin*` became
`LimitUpstreamH2*`, and the two `…WithoutH2c` errors became
`…WithoutHttp2`. Counter and metric names are unchanged.

Behaviour that changes with no config change:
- an inbound `X-Client-Cert-SHA256` request header is stripped on every
  HTTP listener;
- the first health sweep starts up to one `health_interval_ms` after
  startup rather than at once;
- an `http` probe of a `unix:` endpoint without a `host` sends
  `Host: localhost`.

On a deployment that uses TLS at all, whether a listener terminates it or
a cluster reaches an origin over it, the startup banner's libcrypto heap
reads 3 MiB more. That covers up to 256 certificates at the costliest
key accepted. It is a static reservation, and pages a deployment never
uses never become resident.

New config keys:
- on a cluster: `panic_threshold_percent`, `slow_start_ms`,
  `max_total_inflight`, and `retries`' long form `{ "count", "budget" }`;
- `priority` on an endpoint object;
- `passive_ejection.recovery_ms_max`;
- on a listener's `tls`: `client_ca` (`path`, `verify`) and
  `certificates`.

New counters:
- `upstream_ejected_picks`, `upstream_panic_picks` and
  `upstream_standby_picks`, each with a per-cluster family
  (`zoxy_cluster_upstream_*_picks`);
- `l7_shed_total_inflight` and `l4_shed_total_inflight`, with per-cluster
  families;
- `upstream_retry_budget_exhausted`;
- `tls_client_cert_refused`, `tls_rsa_signed`.

The access log gains `client_cert_sha256` on connections whose client
verified. Lines without one are byte-identical to 0.11.0's.
