**Nothing in your config has to change, and if you change nothing this
release behaves exactly as 0.8.2 did.** One ceiling moved:
`limits.relay_buffer_bytes` may now be set as high as 32 KiB on a
deployment that does not terminate TLS. The default stays 16 KiB.

The knob is for one shape of traffic — large response bodies — and the
measurement that moved it says plainly that zoxy was losing that shape
while winning every other one.

## Why the ceiling moved

The cross-proxy nightly runs four 1-CPU proxies, each pinned to one core,
against a four-node origin. zoxy leads it at small bodies and loses at
100 KiB, and the CPU column is what makes that interesting:

| body | zoxy | nginx | zoxy CPU at its knee |
|---|---|---|---|
| 64 B | **62,772/s** | 28,440/s | 0.97 of one core |
| 1 KiB | **61,301/s** | 26,488/s | 0.97 |
| 100 KiB | 4,228/s | 5,838/s | **0.47** |

At 64 B and 1 KiB zoxy is 2.2–2.3x nginx with its core saturated. At
100 KiB it stops at under half a core, while nginx, pingora and haproxy
all reach 0.94–1.00. It is not shedding either: 5,586 of its errors in
that run were timeouts and 85 were connect refusals. zoxy did not run out
of CPU and did not refuse work — it got slow, and a 1 s client timeout
turned the latency into lost throughput.

100 KiB is the first body that does not fit one relay buffer. §6 relays
strictly — recv, send the whole chunk, only then recv again — so at the
16 KiB default a 100 KiB response is 7 chunks, and each chunk is a full
trip out to the event loop and back. That is roughly 14 loop turns per
response. A proxy built on epoll over non-blocking sockets drains the
same body inside a single handler with back-to-back syscalls, so it pays
that queueing delay once or twice where zoxy pays it fourteen times. The
deeper the loop, the wider the gap — which is exactly the shape the table
shows: parity or better at one chunk, divergence at seven.

At 32 KiB the same body is 4 chunks instead of 7.

## The bound that remains, and where it now lives

A terminating listener still cannot take the wider buffer. §4 encrypts a
whole relay chunk into one TLS record with no loop around it, and RFC 8446
§5.1 caps a record's plaintext at 2^14 — so a 32 KiB chunk would produce
a record no conforming peer may accept.

That used to be a ceiling everyone paid, including the plaintext
deployments that have no records at all. It is now a refusal at load
instead: a config that terminates TLS and asks for more than 16 KiB is
rejected with `LimitRelayBufferOverTlsRecord`, naming the reason. §5's
rule, unchanged — a shape that cannot serve is a config error, not a
runtime surprise.

Chunking inside the transform would retire the refusal and let a
terminating listener take the wider buffer too. It is not done here.

## What this release does not claim

**No run has yet measured 32 KiB on that band.** The reasoning above
predicts throughput scales with the reduction in loop turns; the honest
test is one ramp at the new setting, and it has not been taken. This
release makes the setting reachable, nothing more.

Two further caveats travel with the table:

- zoxy's best single window in that run reached 5,452/s and 559 MB/s
  against nginx's 656 MB/s, so raw capability is roughly **15% apart, not
  38%**. The larger figure is the benchmark's sustained metric — the
  highest offered rate still delivering 90% — punishing a collapse past
  the knee rather than measuring the ceiling itself.
- The proxy host's NIC carries proxied traffic twice, and on that fleet
  NIC bandwidth scales with vCPU count. At these byte rates the rig may
  be part of what the numbers show.

The 10 KiB band, which would separate "one chunk" from "many" precisely,
is missing from that run: zoxy failed to start for it. Read the table as
two points either side of a gap.

## Under the hood

Two constants used to alias the relay ceiling and neither should have
followed it up:

- `tls_app_chunk_bytes` sizes every TLS engine's outbox at compile time.
  Dragging it along would have grown **every engine** — on TLS
  deployments that see no benefit — to widen a buffer only the plaintext
  path can use.
- `client_hello_bytes_max` is a property of the record layer. A wider
  relay buffer must not raise how many bytes a peer can make an `l4`
  listener stage while looking for a ClientHello.

Both now pin to the record ceiling directly. The two numbers are
deliberately different, and comptime assertions keep each loader refusal's
legal range non-empty — including the case where one config holds both an
SNI-routing listener and a terminating one against a single global
`relay_buffer_bytes`.

Also in this release: a plain-language editing pass over the manual
(#338) and a refreshed `--check` banner in it (#339).

## Upgrading

Nothing to do.

`limits.relay_buffer_bytes` is the only surface that changed and its
default is unchanged, so an untouched config loads and behaves as before.
Raising it is opt-in, costs memory in proportion — the relay pool is
`relay_buffers x 2 x relay_buffer_bytes`, so doubling the buffer doubles
that term — and is worth considering only if you move large bodies. A
deployment moving small bodies at high concurrency should still be
turning this number *down*.

If any listener terminates TLS, leave it at or below 16 KiB; above that
the config is refused at load rather than failing later on the wire.
