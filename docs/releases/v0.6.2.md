A performance fix. Nothing here changes what zoxy accepts or rejects — only
how much CPU a fragmented request head costs to parse.

## A slow client head could stall the whole loop thread

**Request-head parsing was O(N²) in how many pieces the head arrived in**, and
the client chooses the segmentation. §7's detect-and-retry re-parsed the
accumulated head from byte 0 on every read, so a head that trickled in one
byte at a time cost quadratically more CPU than one that arrived whole.
Measured on a 7.6 KiB head: 5.85 ms of CPU to parse it split one byte at a
time, against 1.6 µs whole. zoxy is single-writer per loop thread, so that 5.85
ms stalled every other connection on the thread — and the shed ladder has no
rung for CPU, only for memory and fds, so nothing intervened.

A per-connection cursor now carries the parse position forward instead of
restarting the scan. A head that arrives whole — the overwhelming majority —
pays what it always paid; a head that arrives in pieces now costs one scan per
byte, not one scan per byte *per subsequent read*:

    whole head (7.6 KiB)   1.66 µs -> 1.57 µs   (no regression)
    64-byte segments       91.1 µs -> 4.5 µs     20x
    1-byte segments        5.85 ms -> 18.4 µs   317x

This is #222's family — burn instead of shed — not a new attack surface: it
makes an existing, always-legal client behaviour (sending a head slowly) cheap
instead of expensive. No protocol or config change; a request that was
accepted or rejected before is accepted or rejected the same way now.

## Under the hood

Building from source outside the pinned `devenv` shell — with no `cc` on
`PATH` — now fails the build with a message instead of silently emitting a
binary that segfaults in `_start`. Zig locates the host's libc by shelling out
to `cc`; without it, detection failed but the build didn't, and every symptom
looked like a bug in zoxy rather than a missing compiler. Release binaries are
unaffected — CI and the release workflow always build inside the pinned
toolchain.

## Upgrading

Replace the binary. No configuration, CLI or behavioural changes.
