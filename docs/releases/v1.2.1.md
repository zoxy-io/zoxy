**zoxy 1.2.1: HTTP/3 under load.** A connection that reached the
request cap no longer loses its last request, and window updates no
longer go out for requests already whole. That second one closed the
connections of clients that took them for errors. Sending is also
cheaper: one ring op carries a connection's datagrams together, and the
connection timer is re-armed far less often.

Replace the binary; no config changes.

## Fixes

- **A connection the request cap retires no longer drops its last
  request.** At `keepalive_requests` (1,000 by default) zoxy sends
  GOAWAY and closes the connection once its last exchange is done. It
  closed as soon as that exchange had handed its answer to QUIC, not
  once the client had it. A closing QUIC endpoint sends CONNECTION_CLOSE
  and nothing else (RFC 9000 §10.2.1). Whatever the client had not yet
  heard was gone, the GOAWAY included. The client saw a clean close with
  a request in flight and no word that it could send it again.

  On the benchmark's c1k-h3 profile that was exactly one failed request
  for each of the load generator's 1,000 connections. Now the close
  waits until the client has acknowledged everything. It waits no
  longer than an idle window after the GOAWAY, so a client that never
  acknowledges holds the connection no longer than a silent one would.
  A drain (`SIGTERM`) closes connections the same way.

- **No window update for a request already whole** (RFC 9000 §13.3).
  After losing a packet that carried flow-control credit, zoxy raised
  MAX_STREAM_DATA again on every request stream it still held, answered
  ones included. A client may have finished with such a stream by the
  time the frame arrived. h3's own client, before zoxy-io/h3#11, took
  that for a frame naming a stream it never opened and closed the
  connection with STREAM_STATE_ERROR. That client is the one zrk 3.0.4
  and earlier are built on. zoxy no longer sends the frame.

## Faster

- **A connection's datagrams go out as one segmented send** (UDP GSO,
  `UDP_SEGMENT`) on io_uring. After a full-size first datagram, one ring
  op carries up to 16 more of the same size, the last possibly shorter.
  A 10 KiB answer used to take eight trips through the kernel's UDP
  stack, and under HTTP/3 load sending was a quarter of the process.
  - Where the kernel refuses a segmented send (no checksum offload, an
    old kernel), zoxy sends one datagram at a time from then on. It
    counts the refusal in the new `zoxy_h3_segments_refused`.
  - Each QUIC binding's send buffers now hold 16 datagrams, about
    760 KiB.
- **The connection timer is re-armed only when it has to be.** QUIC
  moves a connection's deadline on nearly every packet, and each move
  earlier re-armed the timer: a cancel and a fresh arm on the ring. At
  2,000 requests/s on 200 connections that was 5.2 re-arms a request,
  and io_uring's timeout removal was 13% of the process. A target only
  slightly earlier now leaves the armed timer alone, and it fires late by
  at most a sixteenth of the time it had left. That leaves 1.6 re-arms a
  request.
- **h3's send path** (zoxy-io/h3#10):
  - the send buffer shifts with `@memmove` instead of an octet at a
    time, which was 8.9% of the process under HTTP/3;
  - stream buffers are left undefined instead of zeroed, 3%, or 48 KiB a
    request;
  - STREAM frames are sized so a full packet fills the datagram to the
    octet, which segmentation needs.

## Under the hood

- **h3 moves from 7165c3d to 004f04a** (zoxy-io/h3#10, #11 and #12). The
  audits are recorded beside the pin in `build.zig.zon`.
  - #10 also held MAX_STREAMS back until half a window was owed, to save
    a packet each way per request.
  - In the cloud that raised the loss rate and cost a fifth of the
    HTTP/3 throughput, for reasons not found. #12 reverts it, so this
    release sends MAX_STREAMS as 1.2.0 did.
- **`zoxy --check` prices a connection slot 8 bytes larger** (the timer
  records the target it is armed for), and the metrics render buffers
  172 bytes larger (the new counter).

## Checked against

- **The gates.** Every change passed the unit and fuzz corpus, the lint,
  4,096 simulator seeds with the census, and the live gate in both the
  default and the shipped ReleaseSafe build. The simulator segments
  datagrams the way Linux does, each one lost or doubled on its own.
- **The tests.**
  - A server test caps a connection at one request and sends two. On
    1.2.0 the first answer never arrived, on every seed. Now it arrives
    whole, and the second request is refused at the GOAWAY, so the
    client may send it again.
  - h3's tests show that a stream whose request is whole gets no window
    update. They also show that a client keeps its connection when a
    frame arrives late for a stream it has retired. Each test fails with
    its fix reverted.
- **zoxy-io/benchmark's c1k-h3**: 1,000 HTTP/3 connections, 10 KiB
  answers, a ramp past saturation on one core, zrk 3.0.5, against nginx
  in the same run.
  - Run 45110244122, before the cap fix: 1,000 failed requests, one per
    connection, all at t = 199-225 s when they passed their 1,000th
    request.
  - Run 45115190306, with it: none. zoxy completed 1,547,562 requests to
    nginx's 1,564,032, with 469 socket errors to nginx's 599. Its median
    latency was 1.21 ms to nginx's 1.23 ms, and it sustained 5,392
    requests/s to nginx's 5,659.
- **The soak.** A run on this release's code passed: 8 × 500,000
  seeds, 576,000,001 to 580,000,000,
  [run 45157943485](https://github.com/zoxy-io/zoxy/actions/runs/45157943485).

## Upgrading

Replace the binary; no config changes. A connection slot costs 8 bytes
more. A QUIC binding's send buffers cost about 760 KiB, priced in the
banner. Nothing that worked stops working.
