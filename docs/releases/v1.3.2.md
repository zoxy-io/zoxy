**zoxy 1.3.2: TLS failures answered as the RFCs ask, and two fixes the
simulator found.** The simulator now drives much more of what can go wrong
(#491–#500):
- clients that corrupt a TLS record, and origins whose certificate names
  another host;
- HTTP/2 clients and origins that break or bend RFC 9113, and HTTP/3
  clients that break RFC 9114 and 9204;
- every shed rung of DESIGN.md §8.

Those sweeps found two defects in 1.3.1 and settled two TLS behaviours
it left open:

- an HTTP/2 origin's answer to a HEAD lost its `Content-Length`;
- an HTTP/3 request whose end arrived on its own never ended;
- a record that fails to decrypt is now answered `bad_record_mac`;
- a listener offering `h2` alone now refuses a client that names no
  protocol.

Replace the binary. A listener whose `alpn` is `["h2"]` alone, serving
clients that offer no ALPN, needs `http/1.1` added; Upgrading says why.

## Fixes

- **A HEAD's answer from an HTTP/2 origin keeps its length.** The
  origin's declared `Content-Length` never reached the client. The
  HTTP/2 session rightly binds no body to a bodiless answer, and that
  binding was all the answer carried, so the length was lost on the way
  to the HTTP/1.1 head. RFC 9110 §8.6 lets a HEAD's answer drop it, but
  §9.3.2 asks for the fields a GET's would carry. A client that sizes a
  download by HEAD read nothing. A HEAD's 200 and a 304 now keep the
  length the origin declared, with no body.

- **An HTTP/3 request whose end arrives alone now ends.** A client may
  send its request's FIN in a STREAM frame of its own, after the last
  DATA. The `h3` package delivered such a FIN to no reader. It raised
  no `stream_readable`, and it marked the stream read on arrival, so
  the acknowledgement riding the same packet could retire the stream
  unread. zoxy's HTTP/3 server then waited for an end that had already
  arrived, until a deadline ended the request. `h3` is re-pinned to
  zoxy-io/h3#14, which announces a FIN newly in reach and delivers the
  end when the reader asks for it.

## Changed

- **A record that does not decrypt is answered `bad_record_mac`**
  (RFC 8446 §5.2, which makes the alert a MUST). zoxy used to tear the
  connection down without one. The alert is no oracle: only a record
  altered on its way fails, so it tells the sender only what it did.
  - In the handshake it is sent the way an ALPN refusal is, then the
    close lingers. It is counted in `zoxy_tls_handshake_failed` as
    before.
  - On a session that is up, teardown sends it before the write side
    closes, counted in `zoxy_tls_relay_failed` as before. The flush is
    bounded by the deadline the connection already runs, so a client
    that stopped reading cannot hold its slot past it.
  - The alert is skipped when other bytes are still on their way to the
    client, since it cannot be interleaved with them.

  `no_application_protocol`, `certificate_required` and
  `bad_record_mac` are now the only error alerts zoxy sends.

- **A listener offering `h2` alone refuses a client that names no
  protocol.** Such a listener already refused a connection at accept
  when no HTTP/2 session was free, because it has no HTTP/1.1 to fall
  back to. Yet with a session free, it served HTTP/1.1 to a client that
  offered no ALPN at all. HTTP/2 over TLS is reached only through ALPN
  (RFC 9113 §3.2), so that client is now refused at its hello:
  - no ServerHello is sent;
  - no alert is sent, since `no_application_protocol` is for an offer
    with no overlap;
  - it is counted in `zoxy_tls_handshake_failed`.

  A listener whose list also names `http/1.1` is unchanged.

## Under the hood

- **zssl is re-pinned to a0395bd** (zoxy-io/zssl#26). It lets a client
  choose its cipher-suite offer, and it refuses a ServerHello naming a
  suite outside that offer (RFC 8446 §4.1.3). Only the HTTP/3 test
  client sets an offer; the proxy's handshakes are unchanged.
- **`zoxy.testing` grows** what the sweeps drive:
  - the TLS test client can corrupt the record carrying its Finished,
    or its first application record (`Corruption`), and reports the
    alert it heard (`peerAlert`, `heardBadRecordMac`);
  - the HTTP/3 test client can break the rules once on its first stream,
    offer a single cipher suite (`startOffering`) and report the one it
    negotiated;
  - the HTTPS test origin can answer bodiless routes
    (`HttpsOriginRoute`).
- **The coverage report gates on functions** the sweep never enters,
  not on single lines (#487). Line attribution moves whenever the
  program is compiled differently, so a lone missed line now goes in
  the report without failing it.
- **CI's artifact actions run on Node 24** (upload v7, download v8).

## Checked against

- **The gates.** Every change passed:
  - the unit and fuzz corpus and the lint;
  - 4,096 simulator seeds with the census;
  - the live gate, in both the default and the shipped ReleaseSafe
    build.
- **The sweeps that found the fixes.**
  - The sweep's HEAD clients found the missing length. A directed test
    fails without the fix.
  - The HTTP/3 sweep found the lone FIN, and an oracle fails seed 1
    without the re-pin.
- **Mutations of the new behaviour.** Each is caught by the simulator:
  - an engine that never stages the alert;
  - a live session that owes none;
  - a relay that takes a record it cannot open for a fragment;
  - the h2-only refusal removed;
  - a trust check that ignores the origin's name.
- **Eight times the gate's range.** Seeds 1..32,768 pass. Sweeping past
  the gate found two oracle defects in the new TLS sweeps, both fixed
  before merge.
- **h3spec** 0.1.15 on Linux: 86 cases, none failed, and one pending, the
  0-RTT case §12 records.
- **h2spec** 2.6.0 on Linux matched DESIGN §12's recorded deviations.
  - Over h2c, 1 of 146 cases failed, the one §12 records. Over TLS, none
    did, and the drain was clean.
  - The gate counts 145 cases, as the dev shell's h2spec has. The
    upstream release binary used here has 146, so the count was the one
    check it failed.
  - That binary is built with Go 1.12, which offers TLS 1.3 only under
    `GODEBUG=tls13=1`.
- **A kqueue defect that h2spec met on macOS, which 1.3.1 has too:**
  - A client resets a stream whose request has already gone upstream,
    or sends DATA on it, and then closes. On kqueue that connection is
    never released: no deadline reaps it, and a drain waits on it
    forever.
  - On Linux, 120 such connections were all released, and the drain
    finished.
  - Eight h2spec cases each leave one connection held. A proxy's first
    suite fails 9 to 11 cases, the band 1.3.0 recorded. Each later suite
    fails 55, because the eight held connections hold all 8 upstream
    slots. 1.3.1 fails the same, run for run.
  - macOS builds ship for development. The correctness claims are
    io_uring's.

## Upgrading

Replace the binary.

A listener whose `alpn` is `["h2"]` alone now refuses clients that offer
no ALPN. Before, they were served HTTP/1.1. Such clients include
HTTP/1.1-only tools, and probes that never set ALPN. They now fail the
handshake with no alert, and `zoxy_tls_handshake_failed` counts them.
If such clients must keep working, list `"alpn": ["h2", "http/1.1"]`. A
client that offers `h2` is still served it first.

Clients that send corrupted records now hear `bad_record_mac` before the
close, and no counter changes.
