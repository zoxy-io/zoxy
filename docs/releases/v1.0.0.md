**zoxy 1.0: the config's shape is frozen, and zoxy is a library.**
Through every 1.x release, the config's keys stay where 1.0 puts them,
and a key a config leaves out keeps its 1.0 meaning. zoxy is now also a
Zig package that another program builds its own proxy on: configured in
code, with its own endpoint pickers and request policies, on the same
serving path the stock binary runs. For the stock binary there is
nothing to do: replace it, and every 0.12.1 config loads as it did.

## What 1.0 promises

The config's shape is frozen for 1.x (DESIGN §5):

- **Keys stay where they are.**
  - A listener keeps its shared keys and its `http` or `l4` body.
  - `tls` and `proxy_protocol` keep their direction: they terminate or
    receive on a listener, and originate or send on a cluster.
  - Addresses stay strings, and the short spellings stay.
  - `limits` keeps holding reservations only; policy caps stay where
    they apply.
- **An absent key keeps its 1.0 meaning.** No 1.x release turns on, by
  default, a feature that changes where traffic goes or when work is
  refused.

A 1.x release may still refuse a config that only ever loaded by
mistake, as 0.12.1 did for SNI routes to HTTP/2 and HTTPS clusters.
Such a config fails at load or under `--check`, with an error naming
the problem.

What is not frozen is the library seam below. It is published so other
programs can build on it, but HTTP/3 would move the exchange's internal
shape again, and the seam would move with it. A build on the library
pins the version it builds against.

## zoxy as a library

A separate package depends on zoxy, lists its extensions, states its
options in code, and hands them to the same startup sequence the stock
binary runs:

```zig
const App = zoxy.App(.{
    .pickers = &.{LeastInFlight},
    .request_policies = &.{TenantGuard},
});

var least: LeastInFlight = .{};
var tenants: TenantGuard = .{};

pub fn main(init: std.process.Init) !u8 {
    // Endpoint discovery is ordinary code, before the options exist.
    const endpoints = try discover(init);
    const options: zoxy.Options = .{
        .listeners = &.{.{
            .bind = .{ .ip = try std.Io.net.IpAddress.parseLiteral("0.0.0.0:8080") },
            .protocol = .{ .http = .{
                .target = .{ .cluster = "app" },
                .request_policies = &.{App.policy(&tenants)},
                .max_body_bytes = zoxy.defaults.max_body_bytes,
                .keepalive_requests = zoxy.defaults.keepalive_requests,
            } },
        }},
        .clusters = &.{.{ .name = "app", .endpoints = endpoints, .pick = App.picker(&least) }},
        .timeouts = zoxy.defaults.timeouts,
        .limits = zoxy.defaults.limits,
    };
    try App.serve(init, &options, &.{
        .build = .{ .version = "my-edge" },
        .source = "my-edge's options",
        .options_arena_bytes = 0,
    });
    return 0;
}
```

- **Options state every choice.** `zoxy.Options` is typed: addresses
  rather than strings, unions where JSON has a choice of keys, PEM bytes
  rather than paths. No option has a default if it decides where traffic
  goes, when work is refused, or what is reserved. `zoxy.defaults` names
  the stock values, so a build that wants them says so. Options are held
  to every rule a JSON config is: `App.serve` and `App.check` resolve
  them first.
- **Pickers**, one per cluster that selects one. A picker gets the
  endpoints zoxy has already narrowed by drain, retry exclusion, health,
  panic, capacity and standby tier, each with its weight, load, capacity
  and a stable identity. It answers with one of them. An answer outside
  the set falls back to p2c and is counted (`upstream_fallback_picks`).
  zoxy's own `rr`, `p2c` and `hash` are pickers on the same contract
  (`zoxy.pickers`), so a build can select them, or call one from a
  picker of its own.
- **Request policies**, an ordered list per HTTP listener and per route.
  A listener's run after the request is canonicalized and before the
  filters. A route's run once it is chosen and before any connection is
  taken for it. A policy proceeds, or refuses with `400`, `403`, `404`
  or `429`; the first refusal wins, answers with zoxy's static response,
  and is counted (`l7_policy_rejected`).
- **What an extension owes the proxy.** Every call runs to completion on
  the event loop, allocates nothing, and makes no syscall. It depends
  only on its inputs and its own state: no wall clock, and no
  randomness of its own. A picker is handed the loop's monotonic time
  and zoxy's seeded generator, so a seed replays every pick.
- **Testing a build.** `zoxy.testing.Bed` runs a build's own options and
  extensions through zoxy's serving path over the simulator, with an
  origin on every endpoint. `zoxy.testing.expectNoAllocationAfterStartup`
  holds a scenario to the zero-allocation promise and requires a second
  run of the same seed to replay the first exactly.
- **A working example.** [`examples/edge`](../../examples/edge) is a
  separate package with two picker types, one instance of which serves
  two clusters, and a policy at each phase. It ships its own simulator
  tests and a live smoke, and CI builds it against a fetched copy of
  every change.

DESIGN §13 has the contracts, the startup sequence and what is not
offered yet: live endpoint discovery, response policies, and regex in
the stock filters and routes.

## The stock binary

The binary, its config, the JSON Schema and `--check` behave as in
0.12.1. Under the hood, the binary is now one build on the library:

- **The startup sequence moved into the library.** The banner, the
  descriptor budget, the log sink, certificate loading and signals are
  unchanged; `zoxy` and a custom build now run the same code for them.
- **The JSON config is the binary's own front-end.** It reads the file
  and the files the file names, fills in the stock values, and hands the
  library options. The Zig package does not export it, so a custom build
  cannot be configured with zoxy's JSON.
- **The Zig package ships `LICENSE`.** A fetched copy now carries the
  MIT notice it needs, and fetching the package no longer downloads the
  tools zoxy's own benchmarks use.

## Upgrading

Replace the binary. No config that 0.12.1 loaded is refused, and none
changes meaning.

Two refusals read differently:

- **A config with more than one fault** may now be refused for a
  different one of them. A fault only a JSON spelling can have — a
  string no vocabulary holds, a key given twice or not at all, an
  address or CIDR literal that does not parse, a file that cannot be
  read — is now reported before any rule the config breaks. A config
  with a single fault gets exactly the error it got before.
- **A certificate or key file** that is missing, unreadable, empty or
  larger than zoxy accepts now fails the load with
  `ListenerTlsFileUnreadable`, as an unreadable body file does. A
  missing or unreadable one is also named, with the reason, on the line
  before. Each of these failed in 0.12.1 too, later in startup.
  `--check` keeps its verdict, exit 1, and no longer prints the banner
  first.

A program that already imported the `zoxy` module moves to the new
seam:

| 0.12.1 | 1.0.0 |
|---|---|
| `zoxy.config.parse`, `parseWithFiles` | State `zoxy.Options`; `App.serve` or `config.resolve` |
| `zoxy.config_schema`, `zoxy.json_schema` | Not exported; the schema is a release asset |
| `Server(IoType)`, `Budget(IoType)` | `Server(.{ .Io = IoType })`, `Budget(.{ .Io = IoType })` |

New counters:
- `upstream_fallback_picks`, with a per-cluster family
  (`zoxy_cluster_upstream_fallback_picks`);
- `l7_policy_rejected`.

A stock binary runs no extensions, so both stay at zero there.
