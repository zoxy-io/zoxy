A filter can allow. `{ "allow": true }` forwards a request and stops
reading rules, which is what "from this range and nowhere else" needs and
what no combination of the old actions could express. Nothing else in this
release changes behaviour, and no existing config has to move.

## The allowlist was documented, but not expressible

`match.client` has shipped since 0.1.0, and the README described the
allowlist as its standard rule: the admitted range on one rule, a reject
beneath it.

```json
"request_filters": [
    { "match": { "path_prefix": "/admin", "client": ["10.0.0.0/8"] },
      "actions": [{ "header_set": { "name": "X-Internal", "value": "1" } }] },
    { "match": { "path_prefix": "/admin" }, "actions": [{ "reject": 403 }] }
]
```

**That answers `403` to `10.0.0.0/8` as well** — the opposite of what it
reads like. A header edit is not terminal, so evaluation carries on into
the reject beneath and refuses the admitted range with everyone else. Only
`reject`, `redirect` and `respond` ended the walk, and all three *answer*
the request, so there was nothing to put in the rule that was supposed to
admit. Reordering could not fix it, and `match` has no negation, so the
shape was not expressible at all.

The denylist direction — a `client` list on the `reject` itself — always
worked and is unchanged. If you wrote one of those, this release changes
nothing for you.

## `allow`

```json
"request_filters": [
    { "match": { "path_prefix": "/admin",
                 "client": ["10.0.0.0/8", "192.168.1.0/24"] },
      "actions": [{ "allow": true }] },
    { "match": { "path_prefix": "/admin" }, "actions": [{ "reject": 403 }] }
]
```

`allow` answers nothing and edits nothing: it forwards the request and
stops the walk, so the office ranges never reach the `reject` beneath and
everyone else does. Order is the rule, as it is for every filter table —
the admitting rule goes above the refusing one.

Nothing below a matched `allow` runs: not a reject, not a header edit, not
a rewrite. It is not specific to `client` either — any match a filter can
write can be the thing admitted, so "this method on this host, and nothing
else" is the same two rules.

`true` is the only value it takes. An action object names exactly one
kind, so a payload-free action still needs a value; `{ "allow": false }`
is refused at load rather than read as a refusal of its own.

**This is L7 policy, not a firewall.** A request from a refused range still
costs an accepted connection, a parse and a rendered `403`. What zoxy
matches on is the address it actually believes — the TCP peer, or the
PROXY-protocol-announced client on a listener that requires the header —
never an `X-Forwarded-For` chain, which any client can write.

## Under the hood

Two README corrections shipped ahead of the fix, both found by extracting
every JSON block in the documentation and running it through `zoxy
--check`: a redirect example whose second rule could never fire, and the
allowlist claim above, which the docs stated as a known gap until this
release closed it.

## Upgrading

Replace the binary. No configuration change is required, and nothing in
0.8.0's vocabulary moved.

Roll the binary forward before the config: `allow` is a new key, and the
loader refuses unknown ones, so a config using it is rejected outright by
0.8.0 rather than silently ignored.
